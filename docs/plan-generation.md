# Алгоритм генерации план-наряда — `generate_daily_plan()`

Код: `src/services/plan/service.py::AutogenerationService.generate_daily_plan` (и хелперы
`_ready_works`, `_cell_done`, `_cell_started`, `_order_floors`, `_limit_for`, `_load_tech_nodes`).
Решения спеки, на которые опирается алгоритм: Р0, Р1, Р2/Р3, Р6a, Р8 (см. `docs/to-be-plan.md`, §5).

## 1. Назначение и контракт

Строит план-наряд **одного корпуса на один день**: какие работы, на каких секциях/этажах и
каким подрядчиком должны выполняться в дату `target_date`.

```python
async def generate_daily_plan(
    housing_id: UUID,          # локальный id корпуса
    target_date: date,         # день, на который строится план
    section_id: UUID | None,   # опционально: только одна секция корпуса
    force: bool = False,       # разрешение заменить уже существующий день
    actor: str = "system",     # keycloak_id вызвавшего (для ActionLog)
) -> tuple[list[PlanItem], list[str]]   # (позиции, причины)
```

Возвращает пару `(items, reasons)`:
- `items` — созданные (или уже существовавшие, см. шаг 3) ORM-строки `PlanItem`;
- `reasons` — человекочитаемые объяснения, почему часть позиций (или все) не сгенерирована.
  Формулировки — из спеки; фронт показывает их пользователю как warning.

## 2. Источники данных

| Данные | Откуда | Когда читается |
|---|---|---|
| Технологическая последовательность | Локальная таблица `tech_sequence_items` — зеркало **календарного плана (КП)** Рапорта. Нет КП — нет последовательности (DEV-6936): фолбэка на шаблон не существует, задачи КП сами несут `line_number`, `floor_sorting_direction`, `planning_type` | из БД в момент генерации |
| Шахматка (проценты ячеек) | Живой запрос в Рапорт → `services/report_cells` → `HousingSlice`. Ячейка = `(секция, этаж, работа, подрядчик)` с процентом и флагом `is_done` — грань `work_cell_contractor` (Р0) | онлайн, один срез на весь прогон |
| Назначения подрядчиков | Живой запрос в Рапорт → `services/contractor_works` → `HousingAssignments`. Не хранятся у нас (Р1). Назначения уровня секции/корпуса (без этажа) в срез **не попадают** | онлайн, один срез на весь прогон |
| Лимиты позиций | Локальная таблица `contractor_position_limits` (Р8) | из БД |

Важно: шахматка и назначения читаются **до** любых изменений в БД — при недоступном Рапорте
существующий план не пострадает.

## 3. Пошаговый алгоритм

### Шаг 0. Аудит
`log_action(PLAN_GENERATE, housing_id, actor, {date, section_id, force})` — попытка генерации
фиксируется в `ActionLog` всегда, даже если дальше будет отказ.

### Шаг 1. Валидация корпуса
Корпус не найден → выход: `reasons = ["Корпус с таким id не найден."]`.

### Шаг 2. Область дня (scope)
`scope = {housing_id, date}` (+ `section_id`, если генерация посекционная). Всё дальнейшее —
чтение существующих позиций, замена дня, финальная выборка — работает в этой области.

### Шаг 3. Защита существующего дня
Если в scope уже есть позиции и `force=False` — **возврат существующих позиций без изменений**.
Ручной вызов из UI на этот случай отрезается раньше (ручка `/plan-naryad/generate` отвечает 409
«План-наряд на выбранную дату уже содержит позиции… Продолжить?», и фронт переспрашивает).
Ночная джоба (`services/task/service.py`) вызывает генерацию **только** с `force=False` —
собранный и подтверждённый накануне день ночь переживает (DEV-6858 п.5).

### Шаг 4. Загрузка техпоследовательности
`_load_tech_nodes(housing_id)` возвращает два уровня графов:
- `housing_nodes` — общекорпусной граф (строки с `section_id = NULL`);
- `section_nodes[section_id]` — граф конкретной секции, если у неё есть **собственный** КП.

Узел графа (`TechNode`): `work_id`, `order` (номер строки КП), `depends_on`
(финиш→старт-предшественники), `depends_on_ss` (старт→старт), `floor_sorting_direction`
(направление обхода этажей; по умолчанию `asc`). Битые id предшественников не роняют прогон —
пишутся в лог и отбрасываются.

Оба уровня пустые → выход: «Не удалось сформировать план-наряд: для выбранного корпуса не
сформирован календарный план…».

### Шаг 5. Секции
Секции корпуса (или одна выбранная), отсортированные по `section_number`. Нет секций → выход
«У корпуса нет секций.».

### Шаг 6. Срезы Рапорта
Один раз на прогон:
- `slice_ = get_housing_slice(housing_id, work_ids=все работы графов)` — шахматка только по
  участвующим работам (не все ~657 справочника);
- `assignments = get_housing_assignments(housing_id)` — все назначения корпуса;
- `limits = _floor_limits()` — карта лимитов.

### Шаг 7. Цикл по секциям
Для каждой секции:

**7.1. Выбор графа.** `nodes = section_nodes[секция] or housing_nodes` — собственный КП секции
полностью вытесняет общекорпусной; нет ни того, ни другого → секция пропускается.

**7.2. Готовность по этажам.** Для каждого этажа секции считается множество готовых работ —
`_ready_works(nodes, секция, этаж)`. Работа **готова на ячейке**, если одновременно:

1. **ячейка существует в шахматке** — Рапорт знает эту работу на этой секции/этаже. Нет ячейки —
   работы здесь физически нет, планировать нечего (DEV-6858 п.9: без этой проверки работа без
   предшественников «готова» везде);
2. работа здесь **не завершена** — не все подрядчики ячейки в `is_done`;
3. каждый **финиш→старт**-предшественник **завершён на своём ближайшем уровне** (`_dep_done`).
   Составы этажей у работ в КП разные (фундаментная плита живёт только на этаже «-», её
   наследники — на этажах 1..N), поэтому предшественник проверяется каскадом по месту, где
   он вообще существует в шахматке:
   1. ячейки на **этом же этаже** этой секции → все done (строгое поэтажное правило);
   2. иначе ячейки **в этой секции** (любые этажи) → все done;
   3. иначе ячейки **где угодно в корпусе** (включая «Весь корпус») → все done;
   4. нет нигде → «не завершено»: недостающее звено никогда не открывает работу.
4. каждый **старт→старт**-предшественник **начат** по тому же каскаду (`_dep_started`: хоть у
   одного подрядчика ближайшего уровня процент > 0).

Ключевое свойство: там, где предшественник существует поэтажно, готовность **поэтажная** —
«пол сделан на этаже 1» не открывает пол этажа 2. Каскад включается только когда у
предшественника нет ячейки на данном этаже: корпусная работа (принятая на 100% на своём
уровне) открывает поэтажных наследников на всех этажах разом.

**7.3. Фронтир.** Объединение готовых работ всех этажей секции, отсортированное по `order`
(номер строки КП — та самая сортировка автора плана). Фронтир — это не «одна следующая работа»,
а срез готовности всего графа: параллельные ветки идут одновременно.

`order` — это **порядок обхода, а не блокировка**: реальную последовательность задают только
связи графа, и проверяются они поячеечно. Количество *разных* работ на одного подрядчика в день
не ограничено — если во фронтире готовы три работы и на все назначен один подрядчик, он получит
позиции по всем трём — пока суммарно не упрётся в лимит позиций (п. 7.6).

Параллельность при связи **старт-старт**: работа B с SS-предшественником A готова на этаже, как
только A на этом этаже *начата* (`percent > 0` хоть у одного подрядчика ячейки) — завершения
ждать не нужно, обе работы идут одновременно, в том числе у одного контрагента. Практический
нюанс: в день, когда A впервые попадает в план, её процент в шахматке ещё 0, поэтому B в этот же
день не сгенерируется — она подтянется следующей генерацией, после первого факта по A. То есть
«одновременно» на практике означает «со сдвигом минимум в один день от реального старта A».

**7.4. Обход этажей.** Для каждой работы фронтира этажи секции сортируются по
`floor_number` (= `sort_order` Рапорта, ключ порядка — не «номер этажа» для отображения) в
направлении `floor_sorting_direction` работы (Р6a: кровля идёт сверху вниз, монолит — снизу
вверх). Этажи, где работа не готова, пропускаются.

**7.5. Подрядчик.** `assignments.single_contractor_for(секция, этаж, работа)`:
- ровно один назначенный → берём его;
- ноль или **больше одного** → позиция пропускается, в `reasons` добавляется
  «Не назначен подрядчик для работы {работа} секция {секция} этаж {этаж}. Добавьте назначение в
  системе Рапорт.» Неоднозначность сознательно не угадывается. Причины дедуплицируются и
  возвращаются **и при частично успешной** генерации (DEV-6858 п.13).

**7.6. Лимит позиций (Р8).** Счётчик `floors_taken[подрядчик]` — **сквозной по всему
корпусу за день**, не по секции и **не по работе**: лимит по ТЗ — на подрядчика, 4 позиции
«Пола» не оставляют места «Стенам» у того же подрядчика. Значение лимита: персональная строка
подрядчика в `contractor_position_limits` (редактируется в админке, раздел «Планирование»),
иначе `DEFAULT_FLOOR_LIMIT` (конфиг, по умолчанию 4; env-имя историческое). Достигнут лимит —
дальнейшие позиции этого подрядчика в этот день не планируются. Лимит съедается в порядке
фронтира: работы с меньшим `order` в КП получают позиции первыми.

**7.7. Позиция.** В план добавляется строка:

| Поле | Значение |
|---|---|
| `date`, `housing_id`, `section_id`, `floor_id`, `work_id`, `contractor_id` | ключ позиции |
| `source_percent` | процент ячейки **на момент генерации** — снимок для колонки «% Исходный» и базы приращения в сверке (Р6c) |
| `work_cell_contractor_id`, `work_cell_id` | ссылки на ячейку Рапорта (если ячейка со своим подрядчиком найдена) |
| `source` | `auto` |
| `status` | `draft` |

### Шаг 8. Замена дня (транзакционность)

Порядок жёсткий — сначала построить новое, потом удалять старое:

1. **Страховка от потери дня**: если старые позиции есть, новых не построено **и шахматка
   пришла пустой** (`not slice_.cells` — так выглядит сбой Рапорта) → выход «Рапорт не вернул
   ни одной ячейки шахматки по корпусу — существующий план-наряд оставлен без изменений».
   Если же Рапорт ответил, замена применяется даже «в пустоту» — пользователь подтвердил это в
   force-диалоге.
2. `bulk_delete(старые)` + `bulk_insert(новые)` — одна короткая транзакция, коммит в
   `bulk_insert(is_commit=True)`. Падение между ними откатывает всё: день не может остаться
   полупустым.
3. Возврат: свежая выборка по scope + накопленные `reasons`.

### Шаг 9. Пустой результат — объяснение

Если не сгенерировано ничего, `reasons` собирается из (в порядке добавления):
- дедуплицированные «Не назначен подрядчик…» (п. 7.5);
- «Часть ячеек Рапорта пропущена, т.к. сущности не синхронизированы: …» — счётчики
  `slice_.skipped` (ячейка ссылается на секцию/этаж/работу, которых нет в нашей БД);
- если список всё ещё пуст — «Все работы по корпусу уже закрыты либо ожидают завершения
  предшественников.»

## 4. Кто и когда вызывает

| Вызов | force | Дата |
|---|---|---|
| `POST /plan-naryad/generate` (UI) | `false`; при 409 фронт переспрашивает и повторяет с `true` | из запроса, иначе `default_target_date()` |
| Ночная джоба (`/tasks/nightly-plan` ← taskiq Рапорта) | **всегда `false`** — заполняет только пустые дни | `default_target_date()` |

`default_target_date()` (Р2/Р3): до `PLAN_TRANSFER_CUTOFF_HOUR` (по умолчанию 10:00) — сегодня,
после — завтра, потому что сегодняшний план уже ушёл подрядчикам. Час считается по
**бизнес-времени** `APP_TIMEZONE` (`src/utils/business_time.py`, по умолчанию Europe/Moscow) —
от TZ контейнера не зависит (DEV-6978).

## 5. Свойства и сознательные ограничения

- **Идемпотентность без force**: повторный вызов на непустой день ничего не меняет.
- **Rапорт — единственный источник прогресса**: никакие локальные факты в готовности не
  участвуют, только проценты шахматки на момент прогона.
- **Работы корпусного уровня** (ячейка «секция Весь корпус / этаж „-“») планируются как
  обычные — псевдо-этаж полноценен (решение по DEV-6979), подпись «этаж -» честная.
- **Выходных нет** (Р3): алгоритм не смотрит на календарь, джоба гоняет его ежедневно.
- **Назначения только поэтажные**: назначение подрядчика в Рапорте на секцию/корпус без этажа
  до позиции не доезжает (см. `contractor_works`, счётчики skipped) — это осознанное
  ограничение Р1, всплывавшее в DEV-6858 п.17.
- `MAX_ITEMS_PER_CONTRACTOR` объявлен в конфиге, но в генерации **не участвует** — фактический
  ограничитель объёма на подрядчика — лимит этажей (п. 7.6).
- Объёмы (`daily_norm_volume`, `total_volume`) в решениях генерации не используются: спека
  убрала поле «Объём», позиция — это ячейка, а не количество.
- `lag_days` / `lag_between_floors` из КП сохраняются в таблицу, но в решениях о готовности
  **не участвуют** — задержки между работами и этажами алгоритм не отсчитывает.
- Таблица `contractor_position_limits` редактируется в админке («Планирование» → «Лимиты
  позиций»); пустая таблица означает `DEFAULT_FLOOR_LIMIT` (4) для всех.
